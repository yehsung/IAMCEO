## 요약

- **C1 · 높음:** 메시지 재시도 ID가 메모리에만 남는다. 서버가 저장한 뒤 응답을 잃고 앱을 재시작하면, 보존된 초안이 새 ID로 다시 전송되어 같은 지시가 중복될 수 있다.
- **C6 · 높음:** core 팀장 생성 중 응답이 끊기면 살아 있을 수 있는 터미널의 멤버 기록을 삭제한다. 재시도는 새 멤버 ID를 만들어 기존 터미널을 찾는 복구 경로를 끊는다.
- **C3·C4 · 높음:** 다른 기기의 설정 변경과 세션 교체를 검증할 버전이 없다. 오래된 편집 내용이 최신 설정을 덮거나 이미 성공한 새 세션 작업을 다시 실행할 수 있다.
- **C2 · 높음 / C7 · 중간:** 초안은 서버별로 분리되지 않고 첨부는 영속 저장되지 않는다. 다른 호스트의 본사에 이전 초안이 나타나거나 앱 종료 후 첨부만 사라진다.
- **C5 · 높음 / C8·C9 · 중간:** 터미널 입력의 불확실한 결과를 실패와 구분하지 않고, 후처리는 새 입력 초안을 지우거나 다른 기기의 결재 답을 자기 성공으로 처리해 로컬 메모를 버릴 수 있다.

2026-11-07 작업 트리의 정적 감사다. `docs/claude-handoff.md` 전체를 먼저 읽고 네이티브 State·Services·주요 업무 Views에서 HTTP·Store·Orchestrator·core/herdr로 이어지는 경로를 대조했다. 웹 전용 문제는 제외했다. 아래 권고는 **목표 core를 우선**하며 라이브 herdr의 실행 정책 변경을 요구하지 않는다. 크기는 구현·격리 회귀검증을 포함한 상대 크기다(S: 국소 수정, M: 여러 계층의 계약 보완, L: 영속 상태·외부 실행 복구 프로토콜).

이미 있는 보호도 확인했다. 오프라인 마지막 스냅샷 보존과 자동 조회 재시도(`native/Sources/IAMCEO/State/AppStore.swift:169–244`), 프로젝트/연결 세대 검사(`AppStore.swift:139–205`), 동일 메시지 ID 재시도(`server/http.ts:431–455`), 결재 expectedVersion·동일 답 멱등 처리(`server/store.ts:1040–1068`), 재검토 때 선택 해제와 메모 유지(`native/Sources/IAMCEO/Views/InboxView.swift:548–567`), 일반 지시 전송 중 추가 편집 보존(`native/Sources/IAMCEO/State/DraftStore.swift:37–46`)은 유지해야 한다.

실시간 연결·전경 복귀 재검증·스냅샷 역전은 `.pumasi/specs/realtime.md:146–190`, 배경 사건 알림은 `.pumasi/specs/apns.md`, 과거 대화는 `.pumasi/specs/chat-paging.md`, 프로젝트 보관은 `.pumasi/specs/project-manage.md`의 기존 설계로 분류했다. 전달 판정/복구·core 문맥/압축·창 크기는 새 기능으로 재제안하지 않는다. C1은 **아직 서버 접수를 확인하지 못한 최초 메시지의 클라이언트 기록**, C5는 **직접 터미널 조작**, C6은 **직원 생성**의 빈틈으로 기존 전달 큐 복구와 구별된다.

## 우선순위 제안

**완성 전에 꼭**

1. **C1·C6:** 서버에 기록된 작업과 살아 있는 실행을 잃지 않는 것이 먼저다. 최초 메시지 attempt를 영속화하고, core 생성 불명에서 멤버를 삭제하지 않는다. 완료 조건은 “서버는 처리, 응답만 유실 → 앱/데몬 재실행 → 기존 ID로 복원 → 추가 메시지/터미널 생성 0회”다.
2. **C2·C3:** 다른 호스트로의 초안 혼합과 권한 모드의 조용한 덮어쓰기를 막는다. A/B 호스트 모두 hq, 업로드 중 나가기, Mac/iPhone 동시 설정 편집을 격리 fixture에서 확인한다. 실시간 이벤트가 정상 도착하는 경우에도 검증해야 한다.
3. **C4·C5:** 세션 교체와 직접 입력을 열어 둘 배포라면 작업 신원·선행조건·unknown 상태를 먼저 갖춘다. 동일 새 세션 명령의 늦은 재시도, 두 기기의 오래된 설정 적용, Enter 응답 유실, claim 응답 유실을 각각 검사한다. 확정할 수 없는 CLI 부작용을 자동 재생하지 않는다.
4. **C8·C9 및 C7의 업로드 완료 첨부 보존:** 이미 쓴 글·결재 메모·첨부를 성공 후처리나 앱 종료로 잃지 않게 한다. 작은 C8 수정은 더 큰 프로토콜 작업과 독립적으로 처리할 수 있다.
5. **C10:** Mac/iPhone 동시 사용을 완성 범위로 약속하기 전 todo 버전 검증과 결과 조회를 넣는다. 오래된 완료 요청/응답 유실이 추가 완료 알림이나 반대 조작을 유발하지 않는지 확인한다.

**완성 후**

- C7 중 **아직 업로드되지 않은 로컬 파일**의 장기 보존·디스크 한도·보안 bookmark 만료 복구는 별도 확장으로 잡을 수 있다. 업로드가 끝난 첨부 ID 보존까지 미루지는 않는다.
- C1·C4·C5·C6에서 정한 작업 기록을 바탕으로 unknown 지속 시간·자동 복구 횟수·고아 실행 수를 관측한다. 식별자/결과 코드 위주로 기록하고 본문·접속 코드를 진단 로그에 복제하지 않는다. 이 지표가 없으면 같은 오류를 사람이 계속 발견해야 한다.

**하지 말 것**

- polling을 WebSocket으로 바꾸거나 APNs를 추가한 것만으로 C1–C10을 해결했다고 보지 않는다. 기존 설계와 연결하되 영속 작업 신원·CAS·입력 후처리는 별도 수용 기준이다.
- timeout/409를 보고 모든 쓰기를 자동 재시도하거나, 화면 문자열·idle·본문 유사성만으로 수신/완료를 확정하지 않는다. 반대로 결과 조회로 확정할 수 있는 서버 접수까지 사용자가 대화를 읽어 판단하게 두지 않는다.
- 라이브 herdr의 승인 parser/자동 입력 정책을 core에 그대로 이식하지 않는다. 현재 herdr를 재시작하거나 실행기 기본값을 바꾸는 것을 감사 권고의 실행 단계로 삼지 않는다.
- 이미 별도 설계 중인 전달 자동 판정·재전송, 대화 이전 기록, 보관, 실시간 동기화, APNs, 문맥 창/압축을 새 감사 과제로 중복 발주하지 않는다.

## 확인 못 한 것

- **실행 재현 없음:** 코드 열람과 제어 흐름 대조만 수행했다. 서버 7878, 사용자 데이터 디렉터리, config.json, herdr/core 소켓에 접근하지 않았고 실제 Claude/Codex·앱·launchd도 실행하지 않았다. 빌드·테스트를 실행하지 않았으므로 컴파일 성공이나 재현 완료를 주장하지 않는다. 코드 변경이 없고 추가 산출물을 만들지 않기 위한 선택이다.
- C6의 “터미널 생성은 완료됐지만 응답만 사라짐”은 core 코드 자체가 인정하는 실패 가능성(`server/runner/core.ts:119–120`, `server/runner/core-client.ts:44–49`)과 멤버 삭제 경로를 조합한 결과다. 실제 upstream 바이너리가 어느 장애 시점에서 holder를 남기는지 실측하지 않았다. 생성 전 확정 실패까지 모두 고아 실행을 만든다고 주장하지 않는다.
- C1·C4·C5의 중복은 자동 재전송이 이미 있다는 뜻이 아니다. 응답 유실 뒤 사용자의 재시도/앱 재시작 또는 다른 기기의 늦은 요청이 조건이다. 기본 core RPC가 임의 mutation을 자동 재생하지 않는다는 보호(`server/runner/core-client.ts:1–2`)는 확인했다.
- iPhone 실기기의 프로세스 종료·파일 접근 권한·Tailscale 전환, Mac 여러 창과 두 물리 기기의 실제 경합은 확인하지 않았다. UserDefaults/메모리 경계와 await 이후 후처리는 코드로 확인했으며 OS의 실제 종료 시점·저장 flush 시간까지 보장하지 않는다.
- 읽은 `delivery-notice.md`는 제목과 본문이 수동 확인/resolve 중심이다(`.pumasi/specs/delivery-notice.md:1`, `:28–36`). 소유자가 말한 자동 판정 개정안이 별도 진행 중일 수 있으므로 **문서가 다르다는 이유로 수동 확인 설계를 다시 제안하지 않았다.** 기존 문서의 operationId 영속화가 최초 메시지·직접 조작·직원 생성에도 확장된다는 계약은 확인하지 못했다.
- 실시간/APNs/프로젝트·문맥 관련 문서는 설계와 구현을 구별해 읽었다. 외부 작업자가 동시에 파일을 수정할 수 있는 공유 작업 트리이므로 줄 번호는 감사 시점 기준이며, 이 보고서 외 파일을 수정하거나 기존 변경을 되돌리지 않았다.

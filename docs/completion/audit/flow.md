## 요약

- **결재 답·대표 지시·보고의 저장과 후속 전달 등록이 원자적이지 않다.** 중간 종료 뒤 기존 수신자가 있는 항목은 복구 대상에서 빠져, 답했거나 보고했는데 흐름이 멈출 수 있다(발견 1).
- **core에는 입력 도착 이후의 진행 감시가 부족하다.** 턴이 시작되지 않으면 후속 큐가 계속 막히고, 실행 터미널이 사라지거나 필수 보고가 빠져도 총괄에게 필요한 후속 처리가 보장되지 않는다(4~6).
- **완료 취소와 실제 전송이 경합하면 직원에게 잘못된 완료 사실이 남는다.** 결재를 대화에서 정해 닫은 뒤 후속 위임을 빠뜨리는 경로도 시스템이 회수하지 못한다(3, 7).
- **에이전트 도구 재호출·묶음 재정렬·자료 참조 누락 때문에 중복 실행과 잘못된 종합이 가능하다.** 서버가 이미 가진 원본 ID·순서·자료를 끝까지 보존해야 한다(2, 8~9).
- **판 정리와 수동 세션 수신에 별도 복구 사각지대가 있다.** Codex 총괄의 주기 정리 제외, 정리 중 새 변경 누락, 수신 전 완료 처리, 최근 50건 제한을 각각 바로잡아야 한다(10~13).

감사 기준일: 2026-11-07. `docs/claude-handoff.md` 전체를 먼저 읽고, 서버·저장소·MCP 브리지·역할 지침·core/herdr 실행기와 관련 테스트 코드를 정적으로 대조했다. 줄 번호는 감사 시점 작업 트리 기준이다. 코드는 수정하지 않았고, 이 보고서만 작성했다. 심각도는 발생 빈도의 측정치가 아니라 답/지시 손실·중복 실행·무통보 정지의 영향을 기준으로 매겼다. S는 한정된 계약/조건 변경, M은 여러 계층의 상태 전이 변경, L은 영속 기록과 복구 경계 재설계다.

기존 방어도 확인했다. HTTP의 요청 중첩 합류(`server/http.ts:332-340`), 같은 결재 답의 멱등 검사와 다른 답 409(`server/store.ts:1040-1054`), 멤버별 pump 직렬화(`server/orchestrator.ts:2321-2340`), core 미확인 결과의 후속 전달 차단(`server/orchestrator.ts:2365-2366`, `2648-2651`)은 존재한다. 아래 발견은 이 방어가 덮지 못하는 구간이다.

별도 설계와의 경계: 전달 상태 집계·미확인 판정/해소 기능 자체를 다시 제안하지 않는다. 다만 현재 `.pumasi/specs/delivery-notice.md:30-34,264-268`의 내용은 사람이 터미널을 확인하는 수동 해소이며, 요청서가 말한 자동 판정·복구 설계와의 일치 여부는 확인할 수 없다. 이 보고서에서는 **전달 행이 생기기 전의 손실, 도착 후 실행·보고, 도메인 취소 정합성, manual 수신** 등 그 설계가 추가로 받아야 할 경계만 지적한다. 대화 이력·이름/보관·실시간 동기화·APNs·문맥 사용량/압축·문맥 창 수정·웹 전용 문제는 제안 범위에서 제외했다.

## 우선순위 제안

- **완성 전에 꼭:** 1의 원자적 outbox/원본 정합성부터 만들고 2의 agent operation receipt를 연결한다. 이 기반 없이 자동 복구를 늘리면 누락을 살리는 대신 중복 지시를 만들 수 있다. 이어서 3의 완료/취소 보상, 4~6의 core 실행 시작·소실·필수 보고 감시, 7의 명시적인 후속 위임 의도를 처리한다. core를 정상 운영 경로로 삼는다면 이 구간은 대표가 세션을 읽어야 하는 현재 부담을 직접 줄인다. 작은 수정인 10·13·14도 함께 처리하고, manual 지원을 유지한다면 12도 출시 전 수신 계약에 포함한다. 각각 가짜 runner/격리 DB로 쓰기 경계 직후 종료, send 대기 중 취소, started=false 고정, 확정 not_found, post 없는 정상 종료, 응답 유실 재호출, 다른 직원 처리 카드 51건을 검증한다. 실제 작업을 재실행하는 테스트는 필요 없다.
- **완성 후:** 8~9의 순번/assignment/자료를 갖춘 구조화 보고와 11의 board revision 기반 정리를 확대한다. 단, 11의 요청/완료 시각 분리와 실패 상태 노출은 먼저 넣는 편이 작고 효과가 크다. 자동 판 정리를 운영 안정성 장치로 홍보하려면 11 전체도 완성 전 범위로 올린다. 후속 자동화는 보고 수신·검토·업무 상태 반영을 각각 receipt로 남기되, 대표의 결정 내용은 그대로 전달한다.
- **하지 말 것:** idle·빈 화면·시간 경과를 업무 완료나 미전달의 증거로 삼아 원문을 무조건 다시 보내지 않는다. 총괄이 승인 내용을 대신 판단하거나 오래된 인용으로 새 업무를 자동 승인하지 않는다. 동일 본문 해시로 정당한 새 지시를 합치지 않는다. 닫힌 카드/삭제된 수신자를 근거 없이 다른 직원에게 재배정하지 않는다. 별도 전달 안내·대화 이력·동기화/APNs·문맥 설계를 복제하거나 곧 폐기할 웹 UI에만 해결책을 넣지 않는다.

## 확인 못 한 것

- 라이브 7878, herdr/core 소켓, `~/.iamceo` 및 그 config.json에는 접근하지 않았다. 실제 라이브 실행기가 herdr라는 점은 요청서의 전제이며, 이 감사에서 가동 상태를 확인한 사실이 아니다. 현재 소스의 기본 실행기/런타임은 core다(`server/store.ts:193,541-544`, `server/orchestrator.ts:439-442`). 권고는 목표인 core를 우선했고, herdr 경로는 차이의 근거로만 대조했다.
- 실제 Claude/Codex 세션을 실행하지 않았다. 발견 4의 started=false 뒤 무전이, 발견 5의 터미널 소실, 발견 6의 post 누락이 실환경에서 얼마나 자주 발생하는지는 측정하지 않았다. 해당 입력/관측이 발생했을 때의 서버 분기와 복구 부재를 확인한 것이다. core generation 1의 입력 성공이 CLI 업무 수신/실행까지 보장하는지 새로운 실험으로 입증하지 않았다.
- 프로세스 종료·네트워크 유실·동시 요청을 실제로 주입하지 않았다. 발견 1~3·7·11~12는 코드의 DB 쓰기/await/응답 경계를 따라 구성한 재현 경로다. 발생 빈도와 사용자의 실제 피해 건수는 미확인이다. 발견 8의 재정렬 자체는 코드로 확정되지만 모델이 이를 잘못 해석할 확률은 미확인이다.
- 테스트는 관련 소스를 읽었고 실행하지 않았다. 실제 세션/소켓 접근 및 지정 외 파일 생성 가능성을 피하기 위해 빌드·테스트·마이그레이션도 수행하지 않았다. 따라서 기존 테스트 통과나 TypeScript 컴파일 무오류를 이번 작업의 검증 결과로 주장하지 않는다. 보고서만 추가했으므로 export 함수/클래스·외부 패키지 추가는 없다.
- 별도 전달 자동 판정 설계의 이후 개정판·미커밋 외부 작업은 확인하지 못했다. 현재 전달 안내 문서의 수동 해소 범위와 다른 작업자가 만드는 자동 판정 범위가 다를 수 있다. 1·3·4·12의 원자성/취소/실행 시작/manual 경계를 해당 담당과 연결하되, 기존 문서에 이미 있는 unknown 보존·CAS·receipt·core latch 제안 자체는 새 발견으로 계산하지 않았다.

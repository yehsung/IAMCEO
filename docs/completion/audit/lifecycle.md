## 요약

- core 장애는 5초마다 확인하지만, IAMCEO가 소유한 core를 다시 기동하는 경로는 서버 시작 시 한 번뿐이다. 연결 실패 후 재결합 감시도 herdr에만 있다(발견 1·2).
- core 터미널이 사라지면 진행 중 턴을 지우고 offline으로 바꾼다. 이미 전달된 작업은 복구 큐에 없으므로 새 지시가 없으면 중단 사실·재개가 누락된다(발견 3).
- Codex는 native 세션 ID를 수집하지 않으며, 터미널 소실 처리로 paneId까지 지우면 새 세션 자동 생성 금지 조건이 무력화될 수 있다(발견 4).
- 입력 후 턴이 시작되지 않거나 working에 멈추면 core는 무기한 busy가 될 수 있다. 상태 조회 성공과 작업 진전을 구별하는 감시가 필요하다(발견 5).
- 시작 응답 유실 시 멤버 삭제, 종료 확인 전 asleep 저장 때문에 명부 밖 터미널·잠든 것으로 표시된 실행이 남을 수 있다(발견 6·7).

감사 기준: 2026-11-07 작업 트리의 정적 코드. `docs/claude-handoff.md` 전체를 먼저 읽고, 목표 실행기 core를 우선하여 라이브 herdr 및 이전 headless 구현을 대조했다. 심각도는 작업 중단·문맥 유실·고아 실행 가능성 기준이며 실제 라이브 발생을 확인했다는 뜻이 아니다. 크기 S는 국소 수정, M은 여러 계층의 상태 계약 변경, L은 영속 복구 상태와 장애 시나리오 검증이 필요한 범위다.

전달 여부 판정·재전송은 `.pumasi/specs/delivery-notice.md`의 별도 범위로 두었다. 아래의 실행 재개는 **이미 받은 지시를 다시 보내기**와 구별한다. 대화 이력·프로젝트 이름/보관 UX·실시간 동기화·APNs·문맥 사용량/압축·문맥 창 크기 변경은 제안하지 않는다.

## 우선순위 제안

**완성 전에 꼭**

1. **복구의 주체와 재시도 연결부터 완성한다(1·2·9).** 소유 core 기동/hello, 멤버별 재결합, 상태 신선도를 각각 감시한다. core 지연 시작·기동 실패 뒤 회복·일시 소켓 장애에서, 큐가 없는 멤버도 다시 감시되는지 확인한다. 살아 있는 holder에는 새 CLI를 띄우지 않는다.
2. **실행 의도와 종료 의도를 영속화한다(3·6·7).** 최초 run 응답 유실, paneId 저장 전 서버 종료, stop 응답 유실, stop 거절, 각 단계 사이 서버 재시작을 주입하여 같은 operation/member/세대가 이어지는지 확인한다. 명부 밖 터미널, asleep인데 살아 있는 터미널, 풀리지 않은 closing이 없어야 한다. 서버가 꺼진 동안 끝난 실행과 중단된 실행을 구분하고 중단 사건을 한 번만 남긴다.
3. **Codex 세션 손실 보호를 DB까지 연결한다(4).** native ID 수집과 별개로 이전 실행 존재를 잃지 않게 한다. `gone→paneId=null→후속 wake`에서 명시적 인계 없이 terminal.run이 새 Codex 대화를 만들면 실패다. 검증된 native ID를 가진 경우에는 같은 ID resume를 검증한다.
4. **시작 정체·실행 정체와 세션 손실을 분류한다(5·8).** `started:false + turn 불변`, working 장기 고정, 정상적인 긴 도구 실행, 승인 대기, resume 직후 종료를 각각 검증한다. 상태를 추측해 재전송하지 않고 관측 근거와 복구 단계를 남긴다. 전달 판정은 별도 전달 복구 계약을 호출한다.
5. **직접 조작권을 서버 재시작에도 보존한다(10).** 유효 lease 아래 큐를 남긴 채 서버를 재시작하고 자동 send가 0회인지, 같은 terminal에 재claim/release 가능한지 확인한다.

위 검증은 향후 구현의 수용 기준이며 이번 감사에서 실행한 시험이 아니다. core 기본 전환 전에 격리된 fake CLI/소켓으로 먼저 확인한 뒤 허가된 환경에서 실제 재부팅·데몬 장애를 검증해야 한다.

**완성 후**

- 장시간 운용에서 복구 소요시간·반복 실패·중복 기동 거부·미종결 실행 수를 집계하고, 감시 간격/backoff를 조정한다. 고정 시간 초과만으로 정상 장기 작업을 끊지 않는다.
- 같은 supervisor가 서버 자체의 정체도 외부에서 확인하도록 확장한다. 현재 launchd는 프로세스 유지이고 HTTP health는 정적 응답이다(`bin/iamceo.ts:326–329`, `server/http.ts:783`). 실행기 불통만으로 IAMCEO를 재시작하지 말고 서버의 진행 신호와 구별한다.
- herdr를 계속 운영하는 기간에는 구독 재접속 backoff·60초 resync·소유 세션 확인·서버 부재 중 완료 대조를 보존한다(`server/runner/herdr.ts:753–780`, `:1874–1899`, `:1950–1971`; `server/orchestrator.ts:699–707`). core에 부족한 복구 계약의 참고로 쓰되, 폐기할 실행기에 대규모 신규 기능을 추가하지 않는다. headless의 고아 정리도 PID 재사용 검사를 갖추고 있으므로 이를 core holder에 그대로 적용하지 않는다(`server/runner/headless.ts:385–425`).

**하지 말 것**

- socket timeout·hello 실패·화면의 idle만으로 CLI 사망/지시 미전달/업무 완료를 판정하고 자동 재전송·새 세션 생성·일괄 kill하지 않는다. core RPC는 전송 시도 후 통신 실패를 uncertain으로 구분하고 자동 replay하지 않는다(`server/runner/core-client.ts:44–49`, `:73–74`). 이 보호를 완화해 복구처럼 보이게 만들지 않는다.
- `.pumasi/specs/delivery-notice.md`의 전달 판정·복구를 별도 큐/버튼/판정기로 중복 구현하지 않는다. 이 보고서의 실행 기록은 기존 전달 ID·세션 세대와 연결하고, 사람이 세션을 읽어 수신 여부를 결정하는 방식을 최종 자동 복구로 삼지 않는다.
- OS 재부팅 동안 CLI가 계속 실행된다고 약속하지 않는다. 재부팅 후 증거 기반 재결합/재개가 목표다. 사용자 전역 core/herdr나 소유가 확인되지 않은 터미널을 자동 재시작·정리 대상으로 넣지 않는다.

## 확인 못 한 것

- 라이브 서버 7878, `~/.iamceo`, herdr 소켓에는 접속하거나 파일을 읽지 않았다. `~/.iamceo/config.json`도 읽지 않았다. 라이브가 herdr라는 것은 작업 지시의 전제로 받았으며 실제 프로세스·설치 서비스·실행 버전은 확인하지 않았다. 작업 트리의 `createOrchestrator()`는 core 하나를 조립한다(`server/orchestrator.ts:438–443`). 라이브 실행물과 이 소스가 같다고 가정하지 않았다.
- herdr-core upstream 소스/바이너리 내부의 holder 복원, 자체 supervisor, terminal 주소 안정성, 이름 중복 방지의 정확한 원자성은 검증하지 않았다. 저장소에는 버전 0.1.18과 소스 pin 메타데이터가 있다(`vendor/herdr-core/README.md:3–9`). 발견 1은 **IAMCEO 계층의** 재기동 재시도 누락이며 upstream 자체 복구가 없다고 단정한 것이 아니다.
- 실제 macOS 재부팅·로그아웃·절전·강제 전원 종료·SIGKILL·세션 파일 삭제/손상·holder 손실 시험을 하지 않았다. launchd 설치 코드는 `LaunchAgents`/`gui/<uid>`에 등록한다(`bin/iamceo.ts:364–366`, `:396`); 로그인 전 무인 복구까지 검증되거나 보장된 것으로 보지 않았다.
- 실제 Claude/Codex CLI 세션을 띄우지 않았다. 초기 resume 실패가 어떤 exit_code/reason/OSC 순서를 내는지, Codex가 제공하는 native ID 확보 수단, 장기 도구 실행에서 관측 가능한 진전 신호는 제공자별 검증이 필요하다. 발견 4·6·7의 장애 경로는 코드에서 도출했으며 런타임 재현을 주장하지 않는다.
- 기존 테스트는 읽기만 했다. `tests/core-runner.test.ts:73–91`의 재결합·timeout, `:117–121`의 일시 조회 오류 복구는 fake core 서버 기반이다(`:17–62`). 이 시험이 실제 재부팅이나 orchestrator까지 포함한 Codex 손실 경로를 보장하지는 않는다.
- 지정 보고서 외 파일 생성 금지를 지키기 위해 테스트·빌드·TypeScript 컴파일을 실행하지 않았다. 빌드 성공을 주장하지 않는다. 코드·의존성·설정·git 상태를 바꾸지 않고 이 보고서 하나만 작성했다.

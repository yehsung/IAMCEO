## 요약

- **core에는 한도·429·과부하·인증 만료별 복구 정책이 없다.** CLI 오류 뒤 원래 입력은 `delivered`에 남고, 회복 시각에 그 일을 이어가는 예약도 남지 않는다(L1).
- **비용 상한이 실제 실행을 제한하지 않는다.** 동시 턴 수는 headless에만 적용되고, 깨어 있는 직원 수는 초과 후 총괄에게 후보를 알려 주는 권고다(L2·L3).
- **core는 전달 성공 뒤 턴이 시작되지 않으면 무기한 busy가 될 수 있고, CLI가 죽으면 하던 턴 연결을 지운다.** 둘 다 원래 일을 안전하게 이어가는 복구 항목이 없다(L4·L5).
- **연결 복구와 업무 복구가 다르다.** 시작 시 재결합 실패한 core 직원은 대기열이 없으면 감시가 자동 복원되지 않으며, `hello` 성공은 제공자 로그인·한도·직원 상태의 정상 증거가 아니다(L6).
- **herdr의 재시도는 일부 보존 장치가 있지만 회복 시각을 모른다.** 대표 글·결재 답은 3회 뒤 사람에게 돌아가고, 내부 지시·보고는 고정 간격으로 계속 재시도한다. 오류 알림도 대표의 직접 확인에 의존한다(L7~L9).

감사 기준: 2026-11-07 작업 트리. `docs/claude-handoff.md` 전체를 먼저 읽고 서버·공유 타입·관련 테스트를 정적으로 대조했다. 라이브는 지시받은 대로 herdr로 취급하되, 권고는 목표 실행기 core를 우선한다. 현재 소스의 조립은 core 하나(`server/orchestrator.ts:438-443`)이므로 실행 중 배포본이 이 소스와 같다고 가정하지 않는다. 코드·설정·DB 변경, 서버/소켓 접속, 실제 CLI 실행, 빌드·테스트 실행은 하지 않았다.

이미 별도 설계 중인 전달 확인 자동 판정·복구, 대화 이력, 프로젝트 관리, 동기화·APNs, core 문맥·압축과 문맥 창 계산은 신규 제안에서 제외했다. 특히 core 전송 오류를 전부 `delivery_unknown`으로 묶는 문제(`server/orchestrator.ts:2648-2651`)는 `delivery-notice.md`에도 기록된 공백이므로 별도 발견으로 중복 계산하지 않는다. 아래의 **CLI 입력 이후 실행 실패·회복 예약·실행 수 제한**은 전달 확인 설계만으로 해결되지 않는 부분이다.

## 우선순위 제안

**완성 전에 꼭**

1. **L2·L3: 비용 제어를 실행 전 강제한다.** 한도 설정값이 실제 core 배정·재개를 제한하도록 공통 슬롯과 깨어 있는 세션 예약을 먼저 둔다. 한도를 낮췄을 때 기존 작업을 강제 종료하지 않고 새 실행부터 대기시키는 동작도 정한다.
2. **L1·L4·L5: 전달 이후 작업의 생명주기를 보존한다.** 입력 도착과 실행 성공을 구분하고, 오류·실행 미시작·CLI 종료에도 원래 작업 연결이 사라지지 않게 한다. 같은 세션에서 안전하게 이어가기, 확실한 미실행 재시도, 불확실한 부분 실행 보류를 구분한다. quota/auth를 단순 idle이나 일반 실패로 끝내지 않는다.
3. **L6·L8: 재연결과 재개 예약을 영속화한다.** 전송 큐가 없어도 실패한 감시를 되살리고, reset 시각/다음 확인 시각을 지킨다. 단일 probe·슬롯·세션 소유권 확인으로 회복 직후 이중 실행과 호출 집중을 막는다.
4. **L9: 대표가 발견하기 전에 실패 사건을 남긴다.** 기존 알림 설계와 연결하되 APNs 구현을 다시 제안하지 않는다. 총괄의 추가 추론 없이 한도 대기·로그인 필요·설정 오류와 다음 행동을 확인할 수 있어야 한다.
5. **L7: core 구현에 기존 3회 포기·결재 재입력 정책을 이식하지 않는다.** herdr가 계속 라이브인 기간에 동일 정책을 유지한다면 “한도 회복 자동 재개 완료”로 제품 완료 판정하지 않는다. 실서비스 정책 변경 없이 격리 mock에서 먼저 위 시나리오를 검증한다.

**완성 후**

- 실행량이 커진 뒤 프로젝트별 가중치·공정성, 장기간 무진행 관측, 실제 CLI가 지원하는 하위 에이전트 상한을 보강한다(L2·L4). 내부 서브에이전트까지 완전히 제어한다는 보장은 실제 제공자 기능 확인 뒤에만 한다.
- 정확한 비용·잔여 구독 한도를 제공자가 노출하는지 확인한 뒤 출처·신선도와 함께 예산 예측을 추가한다. 현재 코드로 없는 청구액·회복 시각을 만들어 내지 않는다. 최소 운영 제어는 L2/L3/L8로 먼저 완성한다.
- herdr 장기 보강보다 core 공통 오류 정책을 우선한다. herdr에 backoff·차단기를 적용한다면 기존 보고 보존과 입력 중복 방지 회귀를 유지한다(L7·L8).

**하지 말 것**

- 한도·인증·네트워크·모델 오류를 같은 짧은 타이머로 무조건 재시도하거나, 잠자기로 바꾼 뒤 사람이 깨우기만 기다리지 않는다(L1·L8).
- socket 단절, `started:false`, idle, 오류 문구, 기록 부재만으로 미실행을 확정해 원문을 재전송하지 않는다. CLI가 일부 수행한 파일 변경·외부 부작용은 입력 ID만 같아도 다시 발생할 수 있다(L1·L4·L5).
- 수신 확인을 업무 완료로 바꾸거나 이미 답한 결정을 한도 때문에 지우지 않는다. 전달 확인 영수증·미확인 해소 API를 이 보고서에서 따로 설계하지 않는다(L1·L7).
- 과금 한도를 우회하려 자동으로 다른 제공자·계정·유료 경로로 전환하거나, 비용 상한을 맞추기 위해 진행 중 CLI를 무조건 죽이지 않는다(L1~L3).
- 라이브 실행기를 바꾸거나 실제 한도를 소진하는 시험을 하지 않는다. 기존 headless 모의 시험 통과를 core의 복구·비용 제한 증거로 사용하지 않는다.

## 확인 못 한 것

- **라이브 배포·현재 한도·청구 방식:** 7878, `~/.iamceo`, herdr 소켓에 접근하지 않았고 `~/.iamceo/config.json`도 읽지 않았다. 사용자 설명의 라이브 herdr와 현재 소스의 core 조립 차이는 확인한 사실이며, 실행 중 바이너리·설정·계정은 미확인이다. Claude/Codex 계정별 quota 공유 범위, reset 시각, 유료 전환·청구 여부도 추정하지 않았다.
- **제공자 CLI 내부 복구:** 공식 CLI가 자체 429/네트워크 재시도·인증 갱신을 얼마나 수행하는지는 이번 정적 감사로 알 수 없다. L1은 그런 처리가 끝내 실패해 OSC 오류 또는 종료로 드러난 이후 IAMCEO에 재개 정책이 없다는 지적이다. CLI의 모든 일시적 오류가 반드시 사용자에게 노출된다고 단정하지 않는다.
- **OSC 오류·턴 카운터의 실제 시간 순서:** L1의 idle 덮어쓰기, L4의 turn 불변 정체, L5의 종료 누락은 명시된 입력 상태에서의 코드 경로다. 실제 Claude/Codex 버전이 각 오류에서 어떤 OSC sequence를 내는지 실행해 재현하지 않았다. generation 1 구조는 `server/runner/core-client.ts:8-14`로 확인했지만 reset/오류 이력의 추가 공식 수집 수단이 있는지는 검증하지 않았다.
- **복구 정확도의 외부 한계:** IAMCEO 입력 영수증은 CLI가 수행한 외부 부작용까지 보증하지 않는다. 진행 도중 실패한 턴의 안전한 자동 계속하기는 세션 기록·실제 대상 상태·도구별 멱등성에 따라 달라진다. 증거가 없는 부분 실행은 자동 원문 재전송의 근거가 될 수 없다. Codex native ID 손실 시 자동 재개 제한은 기존 `server/runner/core.ts:102-105`를 전제로 했다.
- **시험·빌드:** 관련 테스트 소스를 읽었고 실행하지 않았다. `tests/core-runner.test.ts:87-95`의 불확실 전달 재전송 방지, `117-121`의 이미 bind된 터미널 일시 단절 재접속 검증은 존재한다. 이 두 시험은 L4의 미시작 정체·L6의 최초 bind 실패 복구를 검증하지 않는다. `tests/regress.test.ts:1009-1045`에는 내부 보고 보존과 대표 글 포기 정책이 명시돼 있다. 문서 한 파일만 추가하는 읽기 전용 감사이므로 TypeScript 컴파일 무오류·테스트 통과·실서비스 안정성을 주장하지 않는다.

이번 산출물은 `.pumasi/audit/limits.md` 하나이며 외부 라이브러리 사용과 export 함수·클래스 구현은 없다. 코드 위치는 감사 시점 작업 트리 기준이므로 병렬 변경이 합쳐지면 줄 번호를 재확인해야 한다.

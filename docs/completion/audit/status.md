## 요약

- **높음 — 종료 실패가 ‘잠듦’으로 굳는다.** 실제 CLI 종료 전에 상태를 저장하고, 이후 관측도 asleep이면 무시한다. 살아 있는 세션을 시스템이 숨길 수 있다(발견 1).
- **높음 — core 재연결 실패가 자동 복구 대상에서 빠진다.** 시작 때 한 번 실패하면 큐가 없는 팀원의 상태는 이전 값으로 계속 남을 수 있다(발견 2).
- **높음 — 오류·턴 판정에 역전 경로가 있다.** core 오류 직후 idle이 오류를 덮고, 겹친 조회의 늦은 응답은 상태를 되돌리거나 같은 턴 종료를 다시 발생시킬 수 있다(발견 3·4).
- **높음 — 입력 ACK 후에도 ‘일하는 중’이 영구 고착될 수 있다.** 후속 턴 신호가 없으면 pending을 해제할 감시·정합화 경로가 없다. 미확인 전달 문제와 다른, 정상 ACK 뒤 실행 상태 문제다(발견 5).
- **중간 — 상태·승인·서브에이전트 수·현재 일의 신뢰도를 구분하지 않는다.** 관측 실패, 실제 승인, 미수집 0, 지난 작업 설명이 정상 정보처럼 남는다(발견 6~10).

감사일: 2026-11-07. `docs/claude-handoff.md` 전체를 먼저 읽고 현재 작업 트리의 서버·runner·공용 타입·네이티브 표현을 정적으로 추적했다. core를 권고 기준으로 삼고 herdr의 현행 보호 장치도 대조했다. 파일:줄은 감사 당시 기준이다. **코드 수정·서버 실행·실세션 실행은 하지 않았다.** 크기 S/M/L은 구현과 관련 회귀 검증의 상대 규모다.

## 우선순위 제안

- **완성 전에 꼭:** 1~5. 특히 ‘잠듦’의 실제 종료 확인, 시작 시 core 읽기 재결합 재시도, 오류 결과 보존, 관측·완료의 순서/세대 검증, 정상 ACK 뒤 실행 감시를 core 전환의 필수 조건으로 삼는다. 6~9의 최소 정직성도 함께 반영한다: 마지막 관측/확인 불가, 실제 승인과 미수집 구분, 서브에이전트 미수집≠0, 현재 일의 마지막 보고/갱신 대기. 새로운 명령을 자동으로 보내지 않는 읽기 정합화부터 구현한다.
- **완성 후:** 8의 제공자별 정확한 자식 lifecycle 재구성과 10의 manual 전용 heartbeat 확장. 9의 상태 갱신 요청은 부작용 없는 MCP 경로를 확보한 뒤 고도화한다. herdr는 폐기 예정 엔진의 전면 개편 대신 1·6·8의 공통 계약과 기존 보호의 회귀를 우선한다.
- **하지 말 것:** 전달 확인 자동 판정·복구, 실시간 동기화, APNs, 이전 대화, 프로젝트 보관/이름을 이 감사의 새 작업으로 중복 제안하지 않는다. 문맥 %·자동 압축·창 크기도 기존 `.pumasi/specs/core-context.md:11-19,40-74,76-90` 및 공용 context 수정 범위로 합친다. 현재 코드는 이미 Codex reader를 호출하므로 ‘Codex 수집 코드가 전혀 없다’고 재제안하지 않는다(`server/runner/core.ts:156-181`; `server/runner/codex-context.ts:22-53`). 문맥 신선도/출처·늦은 표본·세션 교체 무효화는 그 설계에서 검증하고, 이 보고서의 4·6과 상태 관측 세대 계약만 공유한다. 웹 전용 UI 문제, 화면 문구로 업무 완료 추정, 일정 시간 무응답이면 자동 재전송/세션 생성, 미확인 승인 자동 선택도 하지 않는다.

후속 검증은 각각 **가짜 terminal/RPC·임시 DB만**으로 다음 불변식을 확인하는 것이 적절하다: 종료 거절 뒤 실제 live와 표시가 일치함(1), 큐 없는 시작 실패 멤버도 읽기 재결합됨(2), error 뒤 idle이 오류 결과를 지우지 않음(3), 역순 응답에도 같은 turn 종료는 한 번임(4), ACK 후 신호 부재에서 자동 send가 0회이며 확인 불가로 수렴함(5), 관측 복구와 unsupported 수치가 사실대로 표시됨(6~9). 이번 감사에서는 시험을 실행하지 않았다.

## 확인 못 한 것

- 라이브 서버 7878, `~/.iamceo` 및 config.json, herdr/core 소켓에 접근하지 않았다. 실제 팀원 상태·설치된 CLI 출력·로그·운영 중 오류 빈도는 확인하지 않았다. 실제 Claude/Codex 세션도 띄우지 않았다.
- 발견 1~3은 호출·저장·이벤트 순서에서 확인한 결함이다. 발견 4의 RPC 응답 역전과 5의 ACK 이후 신호 부재는 코드가 허용하는 조건부 경로이며 실환경 재현 결과가 아니다. 실제 core가 항상 turn을 어떻게 증가시키는지, OSC error/blocked가 설치된 모든 CLI 버전에서 어떤 순서로 나오는지는 별도 fixture·격리 실세션 검증이 필요하다.
- core protocol 타입에 records/reported/kind가 있다는 사실만으로 그 의미·루트와 자식의 분류 정확도를 보장할 수 없다. 발견 7·8은 upstream에서 당장 정확히 추출 가능하다고 단정하지 않으며, 지원 증거를 확인하기 전까지 unknown을 유지하는 권고다.
- herdr의 Agent/Task tool_result가 백그라운드 자식 종료와 항상 일치하는지 확인하지 못했다. 따라서 ‘실제 자식 수와 다를 수 있음’과 재결합 때 EOF부터 읽어 기존 호출을 놓치는 확정 경로를 구분했다.
- 이미 따로 설계 중인 전달 자동 판정·복구의 최신 전체 계약은 확인할 수 없었다. 읽은 `.pumasi/specs/delivery-notice.md:28-34,183-187,264-268`에는 사람의 수신 확인·재전송과 uncertain latch 조정이 기술돼 있다. 소유자가 별도 설계 중이라고 지정한 자동 복구 자체는 중복 발견으로 세지 않았고, 발견 5는 그 설계에 ACK 성공 이후 실행 상태 정합화도 연결할 필요가 있다는 경계만 제시했다.
- 코드와 설계는 감사 중에도 바뀔 수 있다. 문맥 설계의 이전 현황 설명(`.pumasi/specs/core-context.md:7`)보다 현재 `core.ts`·`codex-context.ts`의 구현을 우선했다. 줄 번호는 후속 구현 전에 재확인해야 한다.
- 산출물은 이 보고서 하나다. 소스·설정·git 상태를 변경하지 않았으며, 빌드·테스트는 추가 산출물/캐시나 라이브 의존 실행을 피하기 위해 실행하지 않았다. TypeScript 컴파일 통과를 주장하지 않는다.

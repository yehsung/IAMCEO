## 확인된 핵심

- **1:** 기존 수신자가 있어도 원본만 저장되고 delivery가 없는 답·지시·보고를 남기지 않도록 저장 경계를 묶는다; 이미 설계된 수신 상태 정정과 구분한다.
- **3:** 전송 중 완료 취소는 전송 결과 확정 뒤 정정 알림으로 보상한다; 취소된 항목의 재전송 금지만으로 끝내지 않는다.
- **4:** core 입력 수신 뒤 시작되지 않는 턴이 뒤 큐를 계속 막는 상태를 감지하고 설명한다; 원문을 추측 재실행하지 않는다.
- **5:** core terminal의 확정 소실로 끊긴 진행 업무를 총괄에게 알린다; offline 표시만으로 업무 정산을 대신하지 않는다.
- **6:** core에서 성립하지 않는 마지막 글 자동 게시 약속을 바로잡고, 필요한 결과 보고가 없는 종료를 구별한다.
- **9:** 자료를 연결한 보고의 원본·자료 참조를 총괄 입력까지 보존한다; assignment/work 자동화 전체는 후속 범위다.
- **12:** 지원 중인 manual 일반 wait에 응답 유실 후 같은 지시를 회수할 수 있는 수신 계약을 둔다.
- **13:** manual 답 수신에서 처리 카드 최근 50건 제한을 제거한다; 기존 ID 기반 askWait의 복구 가능성은 유지한다.

## 메모

- **원 보고서에서 구체적으로 다루지 않은 동일 유형: 고아 메시지 복구에도 최근 500건 제한이 있다(중간).** `server/orchestrator.ts:1231`은 `listMessages(..., {limit:500})` 뒤 미전달 원본을 필터링하고, `server/store.ts:1313`도 최대 500으로 제한한다. 메모리 DB에서 delivery 없는 target=null·mine=true·queued 원본 뒤 후속 메시지 501건을 만들자 원본은 그대로 있는데 `orphanMessages()`는 0이었다. 총괄이 없고 이것만 복구 대상이면 `server/orchestrator.ts:1222`도 건너뛰므로 자동 복구 후보조차 되지 않는다. 화면 이력 확장과 별도로, 전체 DB에서 미전달·전달 행 부재를 조회해야 한다.
- **중복 경계:** 최신 전달 설계는 자동 판정·복구 설계다(`.pumasi/specs/delivery-notice.md:1`, `.pumasi/specs/delivery-notice.md:3`). 원 보고서의 수동 해소 문서라는 전제는 낡았다. 수신 상태 transaction·원본 판·unknown 취소 보호는 그 문서로 통합하고, 전달 행 이전 누락·정상 전송 중 보상·수신 이후 실행/보고·manual ack는 남는 경계로 구분했다. 실시간 동기화는 클라이언트 변경 알림이며 CLI 업무 실행 영수증이 아니고(`.pumasi/specs/realtime.md:87`), APNs outbox도 기기 알림용이다(`.pumasi/specs/apns.md:189`); 같은 outbox라는 이름만으로 발견 1을 해결한 것으로 보지 않았다. 프로젝트 이름·보관 설계와 직접 중복되는 발견은 없었다.
- **검증 범위:** 기존 시험 전체와 빌드는 실행하지 않았다. 파일 없는 메모리 재현 및 판 정리의 실패/정상 종료를 분리한 재검증을 수행했고, `./node_modules/.bin/tsc --noEmit --incremental false`는 종료 코드 0으로 통과했다. 재현 스크립트는 저장하지 않았고 새 export·패키지 추가도 없다. 라이브 7878·사용자 데이터 디렉터리·설정·herdr/core 소켓·실제 Claude/Codex 세션과 git 상태 변경에는 접근하지 않았으며, 작성 파일은 이 보고서 하나다.
